# Gravel Rush

რალის სტილის crash-თამაში. გზაზე სამი მანქანაა: მოთამაშე ირჩევს მანქანას, დებს ფსონს და მოგებას იღებს (ქეშაუთს აკეთებს), სანამ მისი მანქანა დაეჯახება ან გაჩერდება.

- **სერვერი წყვეტს ყველაფერს:** შედეგს, ფსონს, ქეშაუთს და ბალანსს. ბრაუზერი მხოლოდ ანიმაციას ხატავს.
- **Provably fair:** ყოველი რაუნდის შედეგის გადამოწმება ნებისმიერ მოთამაშეს შეუძლია.
- **რეალური მულტიფლეიერი:** WebSocket-ით ყველა ერთსა და იმავე რაუნდს ხედავს.
- **დემო კრედიტები:** რეალური ფული არ გამოიყენება.

## გაშვება

საჭიროა Node.js 18 ან უფრო ახალი.

```bash
npm install
npm start               # სამივე სერვისი ერთ პროცესში → http://localhost:3000
npm test                # ყველა ტესტი: მათემატიკა, კონტრაქტი, სერვისები
npm run test:separate   # კონტრაქტული ტესტები სამ ცალკე პროცესზე
```

სერვისების ცალ-ცალკე გაშვება (სხვადასხვა ტერმინალში ან სერვერზე):

```bash
INTERNAL_KEY=საიდუმლო ROUND_PORT=4101 npm run start:round
INTERNAL_KEY=საიდუმლო ROUND_URL=http://127.0.0.1:4101 BETS_PORT=4102 npm run start:bets
INTERNAL_KEY=საიდუმლო ROUND_URL=http://127.0.0.1:4101 BETS_URL=http://127.0.0.1:4102 PORT=3000 npm run start:gateway
```

გარემოს ცვლადები:

| ცვლადი | სად | აღწერა |
|---|---|---|
| `PORT` | gateway | საჯარო პორტი (ნაგულისხმევად 3000) |
| `INTERNAL_KEY` | ყველა | სერვისებს შორის საერთო გასაღები. `npm start` თავად აგენერირებს |
| `ROUND_URL`, `BETS_URL` | bets, gateway | სხვა სერვისების მისამართები |
| `DATA_DIR` | ყველა | მონაცემები. `npm start`-ისას `data/round` და `data/bets` |
| `ALLOWED_ORIGINS` | gateway | სხვა დომენები, საიდანაც WebSocket-ით დაკავშირება შეიძლება |
| `CLIENT_SEED`, `CHAIN_SECRET`, `CHAIN_LENGTH` | round | მხოლოდ **ახალი** ჯაჭვის შექმნისას |
| `BET_MS`, `END_MS`, `SPEED` | round | ფაზების ხანგრძლივობა და დროის აჩქარება (მხოლოდ ტესტებისთვის) |

## მათემატიკა

| | |
|---|---|
| RTP | **97%** ნებისმიერი ქეშაუთის სტრატეგიისთვის (house edge 3%) |
| კოეფიციენტი | `m(t) = e^(0.09·t)`: ×2 7.7 წამზე, ×10 25.6 წამზე |
| გაჩერების წერტილი | `crash = floor(97 · 2^52 / (2^52 − n)) / 100`, n = HMAC-ის პირველი 52 ბიტი |
| ალბათობა | `P(crash ≥ x) = 0.97 / x` |
| დიაპაზონი | ×1.00-დან ზემოთ, **ზედა ზღვრის გარეშე**. ადგილზე გაჩერება (×1.00) დაახლოებით 4%-ში ხდება; ×100-ს აღწევს ~1%, ×1 000-ს ~0.1% |
| მოგების ზღვარი | ერთ ფსონზე მაქსიმუმ **100 000.00** (`MAX_WIN`). ფსონი ამ თანხამდე მისვლისას ავტომატურად იღებს მოგებას, კოეფიციენტზე `floor(MAX_WIN × 100 / ფსონი)`. ეს ერთ-ერთი ქეშაუთის წერტილია, ამიტომ RTP 97% რჩება |
| „დაეჯახა“ / „გაჩერდა“ | 55% / 45%. მხოლოდ ვიზუალია, შანსზე არ მოქმედებს |
| მოგება | `floor(ფსონი × კოეფიციენტი)`, ცენტებში, მთელი რიცხვებით |

| ×1.00 ერთდროულად | ბოლიდები დამოუკიდებელია: ერთი მაინც 11.4%, სამივე `(4/101)³ ≈ 0.0062%` (~16 100 რბოლაში ერთხელ) |

სიმულაცია ნამდვილ ჰეშ-ჯაჭვზე: `npm run simulate` (ნაგულისხმევად 1 000 000 რბოლა, ~10 წმ). ყველა გადახრას სტანდარტულ გადახრებში (z) აჩვენებს და შეცდომით მთავრდება, თუ |z| > 4.

ავტო-ქეშაუთი იგებს, თუ `min(მიზანი, მოგების ზღვრის კოეფიციენტი) ≤ crash`. ხელით ქეშაუთი მიიღება, თუ სერვერის დროით მანქანა ჯერ არ გაჩერებულა.

ფორმულა ერთ ფაილშია, [`public/shared/math.js`](public/shared/math.js), და მას სერვერიც და ბრაუზერიც იყენებს.

## სამართლიანობა (provably fair)

1. პირველი გაშვებისას სერვერი ქმნის საიდუმლო `secret`-ს და 100 000 რგოლიან ჯაჭვს: `chain[k−1] = sha256(chain[k])`.
2. `chain[0]` არის **commit** და ქვეყნდება წინასწარ. ის ჩანს თამაშში, ბლოკში „სამართლიანობის შემოწმება“.
3. რაუნდი `n` იყენებს `chain[n]`-ს. რაუნდამდე ქვეყნდება `chain[n−1]` (ანუ მისი ჰეში), რაუნდის შემდეგ კი თავად seed.
4. მანქანა `i`-ს შედეგი: `HMAC_SHA256(key = seed, msg = clientSeed + ":" + i)` → `crashFromHash`.
5. შემოწმება ბრაუზერშივე ხდება (WebCrypto): `sha256`-ის `n`-ჯერ გამოყენება seed-ზე უნდა მოგვცეს commit, და შედეგები უნდა დაემთხვეს ნაჩვენებს.

> **პროდაქშენში:** `clientSeed` commit-ის გამოქვეყნების **შემდეგ** უნდა აირჩეს, მაგალითად როგორც მომავალი, წინასწარ დასახელებული ბიტკოინის ბლოკის ჰეში. ასე სერვერი ვერ შეარჩევს ხელსაყრელ ჯაჭვს.

## არქიტექტურა

სისტემა სამი დამოუკიდებელი სერვისია. თითოეულს საკუთარი მონაცემები აქვს, და ერთმანეთს მხოლოდ API-ით ესაუბრებიან: ბრძანებებისთვის HTTP/JSON, მოვლენებისთვის SSE.

```
ბრაუზერი ──WebSocket──▶ gateway ──HTTP──▶ bets ──HTTP──▶ round
                           ▲               │  ▲             │
                           └──── SSE ──────┘  └──── SSE ────┘
                           └───────────── SSE ──────────────┘
```

| სერვისი | ფლობს | არ იცის |
|---|---|---|
| **round** (`services/round`) | ჰეშ-ჯაჭვს, ფაზებს, მანქანების გაჩერებას | ფულს, მოთამაშეებს |
| **bets** (`services/bets`) | მოთამაშეებს, ბალანსს, ფსონებს, ჟურნალს | შედეგს წინასწარ (იგებს მოვლენიდან) |
| **gateway** (`services/gateway`) | WebSocket კავშირებს, სტატიკურ ფაილებს | არაფერს წყვეტს, მხოლოდ გადასცემს |

**მთავარი წესი:** შედეგის დამალვაზე და დროზე პასუხისმგებელია round. ქეშაუთისას bets ეკითხება round-ს „დროზეა?“ (`POST /rounds/:n/check`). round პასუხობს კი/არა-თი და გაჩერების წერტილს არ ამხელს.

### round API

| მეთოდი | გზა | აღწერა |
|---|---|---|
| GET | `/health` | ღია |
| GET | `/fairness` | commit, chainLength, clientSeed |
| GET | `/rounds/current` | საჯარო მდგომარეობა (გაუჩერებელი მანქანის შედეგის გარეშე) |
| GET | `/rounds/history` | დასრულებული რაუნდები seed-ებით |
| GET | `/rounds/accepting` | `{round, accepting}` |
| POST | `/rounds/:n/check` | `{car, m100?}` → `{ok, m100}`. `m100`-ით: ავტო (`m100 ≤ crash`); მის გარეშე: ხელით, სერვერის დროით |
| GET | `/events` | SSE: `bet_open`, `race_started`, `car_ended`, `round_ended` |

### bets API

| მეთოდი | გზა | აღწერა |
|---|---|---|
| GET | `/health` | ღია |
| POST | `/players` | `{token?, name?}` → `{token, me}` |
| GET / PATCH | `/players/:token` | `me` / სახელის შეცვლა |
| POST | `/players/:token/refill` | შევსება (< 10.00) |
| GET | `/bets/current` | საჯარო სია (token-ის გარეშე) |
| POST | `/bets` | `{token, car, amount, auto?}` → `me` |
| DELETE | `/bets/:token` | გაუქმება |
| POST | `/bets/:token/cashout` | ქეშაუთი (round-ის დადასტურებით) |
| GET | `/events` | SSE: `bets_changed`, `settled`, `me_changed` (ახალი რაუნდისას ფსონის მქონე მოთამაშეს) |

round-ისა და bets-ის ყველა მარშრუტი (`/health`-ის გარდა) მოითხოვს `x-internal-key` სათაურს. `npm start`-ისას ეს ორი სერვისი მხოლოდ `127.0.0.1`-ზე უსმენს.

### ბრაუზერის პროტოკოლი (gateway, WebSocket)

კლიენტი → სერვერი:
- `hello {token?, name?}`
- `bet {car, amount, auto?}`: თანხა ცენტებში, `auto` ×100-ზე გამრავლებული (მაგ. 150 = ×1.50);
- `cancel`
- `cashout`
- `refill`
- `name {name}`
- `ping {id}`

ყველა ბრძანებას შეიძლება ჰქონდეს `id`. პასუხად მოსულ `me`-ს ან `err`-ს იგივე მნიშვნელობა ექნება `re` ველში.

სერვერი → კლიენტი:
- `welcome`
- `snap`: საჯარო მდგომარეობა. გაუჩერებელი მანქანის შედეგი **არასდროს** იგზავნება;
- `me`: შენი ბალანსი და ფსონი;
- `result`
- `history`
- `err`
- `pong`

## კაზინოების ინტეგრაცია (შუამავალი)

თამაში კაზინოს პლატფორმებთან **შუამავლით** (`services/integrations`) უკავშირდება. კაზინოდან გაშვებული მოთამაშის ფული კაზინოშია: ყოველი ფსონი, მოგება და დაბრუნება კაზინოს API-ს ეგზავნება. დემო ანგარიშები ისე მუშაობს, როგორც ადრე.

```
კაზინო ──LaunchGame──▶ /p/<პლატფორმა>/…  (gateway → integrations) ──▶ თამაშის ბმული ?session=…
ბრაუზერი ──WebSocket──▶ gateway ──▶ bets ──▶ integrations ──ადაპტერი──▶ კაზინოს /balance, /transactions
```

- **ბირთვი** (`hub.js`): სესიები, ტრანზაქციების ჟურნალი (ერთი id ორჯერ არ ტარდება), ფრიბეტები. პლატფორმაზე არაფერი იცის.
- **ადაპტერი** (`adapters/*.js`): ერთი პლატფორმის პროტოკოლი. ახლა არის `upgaming` („Upgaming Reverse Integration“).
- **ახალი პლატფორმის დამატება:** იხ. [`services/integrations/adapters/README.md`](services/integrations/adapters/README.md). საჭიროა ერთი ფაილი, ერთი ხაზი რეესტრში და კონფიგურაცია.
- **ფსონების სერვისი:** მოგება და დაბრუნება რიგით (`outbox.json`) იგზავნება ხელახალი ცდით, ყოველთვის იმავე id-ით. თუ ფსონზე პასუხი არ მოვიდა, უსაფრთხოებისთვის დაბრუნება ემატება რიგში.

### სატესტო კაზინო

`npm start` ავტომატურად უშვებს Upgaming-ის იმიტაციას: **`/demo-operator/`** (მაგ. `http://localhost:3000/demo-operator/`). მასში სამი მოთამაშეა (GEL, USD, EUR), ბალანსი კაზინოს მხარესაა. „თამაშის გაშვება“ სერვერიდან იძახებს ჩვენს `LaunchGame`-ს და თამაშს იმავე გვერდზე ხსნის. ტრანზაქციების ცხრილში ჩანს ყოველი BET / WIN / ROLLBACK. გამორთვა: `DEMO_OPERATOR=0`.

### რეალური პლატფორმის კონფიგურაცია

`INTEGRATIONS` (JSON) ან `INTEGRATIONS_FILE` (ფაილის გზა):

```json
[{
  "id": "upgaming", "adapter": "upgaming",
  "operatorId": "…", "providerId": 123,
  "walletUrl": "https://<Upgaming-ის მისამართი>",
  "hashKey": "<Upgaming-ის HashKey>",
  "currencies": ["USD", "EUR", "GEL"],
  "allowedIps": ["…"]
}]
```

Upgaming-ს მიეცით: `https://<ჩვენი დომენი>/p/upgaming` (GetGames, LaunchGame, AddFreeBet, CancelFreeBet). თამაშის ბმულის დომენი: `PUBLIC_URL` (Render-ზე ავტომატურად `RENDER_EXTERNAL_URL`).

### Upgaming-თან დასაზუსტებელი

სპეციფიკაცია რამდენიმე ადგილას ორაზროვანია. ამიტომ შესაბამისი პარამეტრები კონფიგურირებადია, ნაგულისხმევი მნიშვნელობები ფრჩხილებშია:

1. **ჰეშის ალგორითმი:** გვ. 3-ზე SHA512, გვ. 8-ზე SHA256 (`hashAlgo: "sha512"`).
2. **სათაურის სახელი და ფორმატი:** „SecretKey“ სათაურის სახელია? მნიშვნელობა `SHA-512=<hash>` hex-ია თუ base64? (`hashHeader: "SecretKey"`, `hashPrefix: "SHA-512="`, `hashEncoding: "hex"`)
3. **Upgaming-ის ჩვენთან მოთხოვნები** (LaunchGame და სხვ.) ჰეშით მოდის, თუ მხოლოდ IP-ების სიით მოწმდება? (`allowedIps`)
4. **წაგებული რაუნდი** WIN 0-ით უნდა დაიხუროს? (`closeRoundWithZeroWin: true`)
5. **გამეორებული ტრანზაქცია:** `TRANSACTION_ALREADY_PROCESSED` (403) თუ თავდაპირველი წარმატებული პასუხი? ადაპტერი ორივეს წარმატებად თვლის.
6. **ფორმატები:** `roundid` GUID უნდა იყოს? `gameId` LaunchGame-ში Integer-ია, სხვაგან String.
7. **WIN ამოწურულ სესიაზე:** მიიღება, თუ `SESSION_EXPIRED` ბრუნდება?
8. **FREESPINWIN და ფრიბეტები:** Riviera Rush crash-თამაშია. ფრიბეტები ინახება, მაგრამ თამაში ჯერ არ იყენებს (`FreespinSupport: false`).
